# M13 — Attachment intelligence

## Goal
Extract useful text from stored attachments and let the owner confirm a
suggested type and fields before filing them.

## Exact files or areas expected to change
- `app/files/` and `app/db/files.py`: represent extraction results and
  customer-folder placement.
- `app/providers/` or a local extraction area: provide PDF text extraction and
  local Tesseract OCR behind small interfaces.
- `app/reply/` or application services: request an LLM suggestion for type and
  fields only after safe preprocessing.
- `app/ui/customer_files.py` and related screens: display suggestions and require
  owner confirmation.
- Tests with representative local fixture files and failure cases.

## Acceptance criteria
- Tests show text can be extracted from a text PDF and OCR is attempted for an
  image attachment.
- The system produces a suggestion for attachment type and fields without
  silently filing it.
- An owner confirmation puts invoices and contracts in the correct customer
  folder.
- Unsupported, unreadable, or ambiguous files are retained and escalated.
- No attachment leaves the machine unmasked before an external API call.

## Security/safety constraints
- Keep attachments and extracted text out of logs and committed fixtures when
  they contain personal data.
- Require owner confirmation before changing customer filing or using a result
  in a reply.
- Apply M10 masking before any cloud call; prefer local extraction first.
- Sending remains subject to M12 approval and is not part of Phase 1.

## Out of scope
- Automatic filing without confirmation.
- Payment processing, accounting integration, or contract decisions.
- New external API integrations beyond the interfaces already planned.
- Implementing this milestone during Phase 1.
