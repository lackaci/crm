# M10 — Personal-data masking

## Goal
Mask sensitive personal data before any external model call and safely restore
the masked values after the response, with a debug preview.

## Exact files or areas expected to change
- `app/reply/` or a small privacy module: masking, placeholders, and restoration.
- `app/providers/`: ensure every outbound LLM path uses the masking boundary.
- `app/ui/`: add a debug-only “what we send” preview.
- `app/db/` and audit code: ensure previews and audits do not store raw
  sensitive values.
- Tests for card numbers, IBANs, ID numbers, similar configured patterns,
  restoration, and provider-call boundaries.

## Acceptance criteria
- Tests prove recognized sensitive values are replaced before a provider sees
  text.
- Tests prove masking also applies to every real-LLM call path, not just the
  main screen.
- A successful safe response restores only the matching placeholders.
- An ambiguous or failed restoration escalates and does not create a sendable
  draft.
- The debug preview shows masked text and never raw sensitive values.

## Security/safety constraints
- Mask before data leaves the machine; do not rely on the provider to protect
  it.
- Do not put original values in logs, audit records, prompts, errors, or test
  fixtures.
- Treat uncertain matches conservatively and escalate.
- Sending remains disabled until M12, and Phase 1 performs no real API work.

## Out of scope
- Gmail synchronization or OAuth.
- Attachment text extraction and OCR.
- Choosing provider-specific masking services.
- Automatic sending, auto-approval, or a full GDPR deletion workflow.
