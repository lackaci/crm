# M14 — Hardening

## Goal
Make the integrated prototype safer to operate by adding a kill switch,
limits, clear failures, backup/export, and customer deletion.

## Exact files or areas expected to change
- `app/`: add a kill switch that pauses all AI activity and rate limiting.
- `app/ui/`: add pause controls and plain-language error screens.
- `app/db/` and audit code: support safe export, deletion, and evidence of
  administrative actions.
- Configuration and provider boundaries: ensure paused or limited operations
  cannot bypass safeguards.
- Tests for pause, limits, errors, backup/export, and delete-customer behavior.

## Acceptance criteria
- A test proves the kill switch prevents new AI/provider calls until resumed.
- Rate limits stop additional calls and show a clear, non-secret error.
- Export creates a usable backup, and delete-customer removes the defined
  customer data while preserving required audit integrity.
- Provider and send failures are visible in plain language and leave safe
  recoverable state.
- Existing offline tests and golden evaluations still pass.

## Security/safety constraints
- Default to the safest state after restart or configuration failure.
- Do not expose secrets or personal data in errors, exports intended for logs,
  or audit messages.
- Keep every provider call, send, approval, pause, and deletion auditable.
- Never bypass M10 masking, M12 approval, or the send allowlist.

## Out of scope
- New API integrations, provider selection, or model changes.
- Removing owner approval or enabling unrestricted automatic sending.
- Production compliance certification or promises beyond PLAN2.
- Any hardening implementation during Phase 1; Phase 1 adds specifications
  only, and real API work is not included.
