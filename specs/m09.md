# M09 — Cloud LLM provider

## Goal
Add a real `LLMProvider` implementation behind the existing interface, while
keeping the reply pipeline testable with the fake provider.

## Exact files or areas expected to change
- `app/providers/llm_cloud.py`: implement the cloud provider adapter.
- `app/providers/llm_base.py`: change only if the interface needs a justified,
  backward-compatible clarification.
- `app/reply/`: connect the provider and versioned prompts.
- A prompt/configuration area: store prompt versions as files, not scattered
  inline strings.
- `app/db/` and audit-related code: record provider calls, model, prompt
  version, FAQ id, token use, and cost as specified by PLAN2.
- Tests and offline golden-evaluation integration.

## Acceptance criteria
- A test can substitute `FakeLLMProvider` and run without network access.
- The cloud adapter calls only through `LLMProvider` and has timeouts and
  bounded retries.
- Responses requested as structured JSON are validated, and malformed output
  is handled safely.
- Each provider call produces the required audit information.
- The reply pipeline passes the golden set without increasing wrong drafts or
  missed escalations.

## Security/safety constraints
- Real calls are not part of Phase 1; use fakes and tests while these specs
  are being created.
- Never send a prompt containing secrets or unmasked personal data; M10 must
  be completed before real customer data is used.
- The model may only rewrite an owner-approved FAQ answer. It must not answer
  from its own knowledge.
- Preserve escalation rules and keep sending disabled until M12.

## Out of scope
- Gmail or OAuth integration.
- Personal-data masking implementation (M10).
- Attachment intelligence.
- Automatic sending, Live mode, or provider-specific behavior not stated in
  PLAN2.
